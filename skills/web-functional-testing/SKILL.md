# Web functional testing

Design and execute fresh tests for each assessment. Use the user's requirements, product documentation, live UI, product source, and independently derived expected results. Exclude the target repository's existing tests, test fixtures, snapshots, and prior results from discovery, generation, execution, and coverage. A framework or interpreter already installed in the workspace can run the new test files. Keep its test collection and setup isolated from the target's suite.

Use [independent test design](references/independent-test-design.md) to choose applicable scenarios even when the README is sparse. If only a URL is available, discover the workflows in the browser and author fresh black-box checks. Record a gap when an intended outcome or source-level test cannot be established.

Resolve bundled files relative to this `SKILL.md`. Run commands from the target workspace and keep generated tests and reports there. Use the project's existing runtime and approved browser tools. The report renderer and CSV generator use the Python standard library. The page inspector, polling helper and Edge demo use an existing Python Playwright environment. When that environment is unavailable, use available browser tools and the app runner for the checks they support, then record remaining coverage gaps.

1. **Inventory requirements and user journeys.** Follow [README-driven testing](references/readme-driven-tests.md). Link each testable claim to its source and implementation, assign a requirement ID, and record the checkout revision when available. Prioritize the smallest normal path, incorrect results, state bugs, and promised features with missing behavior.
2. **Design and author an independent suite.** Write fixtures and expected outcomes before running each case. Generate unit checks for isolated contracts, integration checks for real boundaries, and browser checks for visible journeys. Save the new cases in `exploration_tests/<run-id>/` or an isolated workspace. If a runtime is unavailable, record the gap and continue with the accessible layers.
3. **Explore and run the GUI cases.** Read [the functional workflow](references/functional-workflow.md). Inventory pages, states and role-specific entry points with approved browser tooling or [the page inspector](scripts/inspect_page.py). Use observed locators, isolated contexts, and uniquely owned QA data. Execute the new smoke case before broader coverage. Verify the current outcome before repeating an ambiguous write.
4. **Synchronize.** Read [waiting for completion](references/async-completion.md) for asynchronous work. Register event waits before triggering an action. Correlate the operation with its job, result version or record ID. Prefer a definitive business-ready UI signal or a documented job/status endpoint. Use [the bounded polling helper](scripts/wait_for_job.py) for a known JSON job contract, then verify the actual UI/data/file result. Poll reads only. Trace accepted, running, terminal failure, timeout and result mismatch independently.
5. **Increase input size after correctness.** Follow [capacity testing](references/capacity-testing.md) on the authorized local or QA environment. Use the [CSV generator](scripts/make_csv_fixture.py) for a bounded synthetic fixture when applicable. Start with one small input and one worker. Scale one dimension at a time within the stated budget, assert output integrity at each step and record both limits and graceful rejection. A failing functional baseline blocks load escalation on that path.
6. **Report and recommend.** Follow [the reporting contract](references/reporting.md). Save `coverage.json` in a run-specific folder and run the [report renderer](scripts/render_report.py). Tie each executed case to a new test file or recorded browser steps, the expected-result source, and evidence from this run. Preserve the new tests and evidence, including failures and gaps. Product code changes require a separate request.

For a remote app, use existing approved model and browser access. Keep source and artifacts in English and communicate in the user's requested language. If a genuine blocker limits coverage, document it and complete the independent scenarios that remain accessible.

Use the [sample Copilot request](references/copilot-request.md) to see what project inputs to provide. The [synthetic samples](samples/README.md) include a file-only walkthrough and an optional localhost demo for checking a new installation. Keep generated sample output outside the Skill. The [browser requirements lock](requirements-browser.lock) is available when an approved package setup is needed.
