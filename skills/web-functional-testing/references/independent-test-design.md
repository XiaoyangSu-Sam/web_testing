# Independent test design

## Derive fresh cases

1. **Discover the product.** Start with in-scope user journeys, the README or specification, and the actual web UI. Record entry points, roles, controls, input formats, states, and observable effects. Use product source to locate logic and identify branches worth testing. Exclude existing test/spec files, test-only fixtures and helpers, snapshots, and prior reports from searches and context.
2. **Design the case before measuring its result.** Record the requirement or property, starting state, data, action, expected result, and expected side effects. Use at least a normal case and a relevant negative, boundary, or recovery case for critical journeys when scope and access permit. Use equivalence classes for inputs, neighboring values for documented limits, decision tables for interacting rules, and state transitions for lifecycle rules. [ISTQB Foundation Level Syllabus, section 4.2](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
3. **Choose an independent expected result.** Use explicit product rules, approved examples with known outputs, an applicable public standard, or a small known input with an independently calculated answer. Use a property implied by the contract when a full exact answer is impractical. Comparing the UI to an export can establish consistency. Verifying correctness needs an independent expected result. If discovery already revealed the output, choose fresh inputs for the asserted case. Report gaps when the intended outcome cannot be established.
4. **Implement and execute your own cases.** Write new tests and setup under `exploration_tests/<run-id>/` or in an isolated workspace. Reuse available tool binaries and product interfaces. Invoke the fresh files by path with isolated configuration so the runner cannot collect the project's suite or auto-load its test hooks. A standalone script or recorded browser procedure works when the suite cannot be isolated. Use a clean browser context, new test data, user-facing locators, and assertions that wait for observable outcomes. [Playwright best practices](https://playwright.dev/docs/best-practices)
5. **Record independent evidence.** Save the new case or script, the expected-result basis, the observed result, and the command or browser steps. Count only cases executed and assessed in this run. Discovery-only probes help design cases and can record observations. Use `exercised_unverified` when a case ran without an established business expectation.

## General Web coverage

Select cases for features the app actually exposes. Record blocked cases when roles, environments, or inputs are missing. A pattern supplies test ideas. Derive values, boundaries, and assertions for the actual product contract.

| Capability | Cases to design | What to verify |
| --- | --- | --- |
| Entry and navigation | Smoke test the entry point and core journey. Try tabs, deep links, back/forward, and refresh where supported. | Correct page, record, and role. Filters or unsaved edits follow the documented navigation behavior. |
| Forms and validation | Valid input, required input omitted, whitespace or invalid format, and values just below, at, and above documented limits. Try correction after rejection. | The correct field and failure are identified. Accepted data matches the contract. Rejected inputs leave records unchanged. |
| Writes and workflow | Create, update, cancel, or review an owned QA record. Cover allowed and disallowed documented state transitions and repeated submission where in scope. | Exact stored values and record ID, actor and resulting state, and the result after reload. Verify the number of writes when uniqueness is part of the contract. |
| Lists, search and query tools | Empty and nonempty results, duplicate sort keys, first and last pages, clearing filters, changing a query mid-session, and canceling supported work. | Exact rows, order where specified, filter and paging consistency, and result identity. Use a fixture with known rows before trying larger volumes. |
| Calculations and data views | Negative, zero, fractional, and missing values where supported. Vary grouping, rounding, and precision. | Independently calculated cells, totals, and defined treatment of missing data. Check the same business result after a relevant state change. |
| Upload, import and export | A small valid file, empty or invalid schema, supported encodings and separators, and a documented size limit when approved. | Parsed data, expected acceptance or rejection, exact rows and fields in export, and persistence. |
| Asynchronous work and recovery | Accepted, running, terminal success/failure, controlled delays, cancellation, or two consecutive operations. Use a test environment or fixture for induced failures. | Each result matches its own job ID. Previous results cannot satisfy the current assertion. Recover safely and check the final state before retrying a write. |
| Roles and session | Exercise normal app flows with authorized roles and a known signed-out or expired session when available. | The documented action and recovery path for each role. Record UI visibility and backend behavior only for the surfaces exercised. |
| Keyboard and layout | Navigate key controls with a keyboard, check focus and labels, provoke a form error, and check narrow-layout reflow where applicable. | Critical controls remain reachable and usable, and errors identify the affected field in text. A targeted check supports only the specific criteria tested. [WCAG 2.2](https://www.w3.org/TR/WCAG22/) |

## Example with a known result

For a documented decimal sum, choose three new rows with amounts `12.50`, `-2.25`, and `0.75`. Calculate the expected total `11.00` before running the application. Write a new browser test that loads those rows, verifies that the displayed result belongs to this input, and asserts the exact total. If export is supported, parse the downloaded file and compare it to the same known rows and independently calculated result. A displayed and exported total of `11.75` is a calculation failure even though the two surfaces agree. Tie any pass or failure to this new test and this run's evidence.
