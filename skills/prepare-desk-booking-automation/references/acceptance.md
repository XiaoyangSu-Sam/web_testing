# Desk Booking acceptance cases

Exercise the normal entry point with fresh synthetic inputs and record the expected result before each run. Derive expected desk, account, reservation state, and write counts from the scenario setup and booking rules. Isolate the fixture URL, output directory, attempt journal and browser profile. Use the fixture's observed action counts to assert side effects. Keep browser and CLI evidence tied to the test run. For a production read-only smoke test, use the approved site and account and compare visible evidence for a known slot. Record cases without available live evidence as unverified.

| Case | Acceptance result |
| --- | --- |
| Fresh-chat request to reserve a specific desk for one date | Copilot loads the existing Desk Booking Skill, routes once to the single-date CLI, completes the fixture workflow with an established session, and reports one matching verified reservation without further input. |
| Booking with configured defaults and Chinese wording | A request such as `帮我订明天的工位` resolves the date from the site's timezone and uses the configured desk, location, and hours. The fixture shows one reservation for the intended date only. An unspecified date uses the existing documented booking scope. |
| Check or dry run | Known available, occupied and unknown fixture results are distinct. A multi-date check reports dates after an unavailable date within its budget. Cart add and submit counts are both zero. |
| Fresh scope and exact matching | A stale grid and similar IDs never trigger a booking. An independently confirmed fresh result with the same content can progress. Validate exact location and interval. An overlapping reservation blocks the requested interval and an adjacent interval is classified using the site's supported boundary rule. |
| Alternative policy | `never_fallback` finishes with the original desk's outcome. Ask mode lists alternatives with zero adds and submits. A later explicit choice uses fresh evidence. Automatic fallback reports the requested desk's reason and the actual verified desk. |
| Submit and verify | One real fixture submission produces a matching new record in My Events. A pending record is reported as pending. A generic dialog, record for the wrong account or slot, and an older matching reservation cannot establish success for this run. |
| Possible submit or interruption | Simulate a commit with delayed or lost confirmation. Recover the verified record via read-only reconciliation or return `uncertain`. Repeat the request and assert that the unresolved attempt does not cause a second submit or alternate booking. |
| Multi-date write flow | After applying the configured fallback policy, stop at the first unavailable, failed, or uncertain date. Report any earlier verified reservations and mark later dates as unattempted. |
| Session or site change | Expired login routes to the existing SSO recovery. Wrong account, missing scope, unreadable journal, or ambiguous controls preserve the relevant failure reason and produce no submit. |
| Runtime and cleanup | Capture time until the current run yields a verifiable result and time until the process exits. Compare serial warm runs on identical fixture inputs. Verify that slow cleanup leaves the previous result attributable to its run and cannot permit concurrent reuse of its profile. |

For each implemented test, keep the exact command or prompt, input fixture, expected and observed behavior, pass status, and evidence. When available, use the Web Functional Testing Skill's `coverage.json` and report renderer. Report the live authentication, page semantics, and write/read-back checks at their actual verification level. Run a live write smoke only when the user separately requests a real reservation and provides or has configured its scope.
